# EMMUS 2.0
**Detailed Software Design**
**Document Phase:** Phase 3 — Detailed Software Design
**Project:** Enhanced Memory Management Unit Simulator (EMMUS)
**Project Type:** Software / Systems Engineering Portfolio Project
**1.1 Purpose:**
This document defines the detailed software design for the Enhanced Memory Management Unit Simulator (EMMUS).
Phase 1 established the system purpose, scope, functional requirements, non-functional requirements, and success criteria.
Phase 2 established the system architecture, subsystem boundaries, architectural principles, dependencies, and major interfaces.
Phase 3 translates those architectural decisions into detailed software designs that can be used as the foundation for implementation.
This document defines:

This document is intended to provide sufficient technical detail for implementation while avoiding unnecessary commitment to source-code details that should remain implementation-specific.

2. Design Objectives
The detailed software design shall satisfy the following objectives.
2.1 Correctness
The implementation shall faithfully implement the requirements and architectural behavior defined in Phases 1 and 2.
2.2 Clarity
Classes and interfaces shall have clear responsibilities and understandable relationships.
2.3 Maintainability
Components shall minimize unnecessary coupling and avoid hidden dependencies.
2.4 Testability
Core components shall expose behavior that can be verified through automated tests without requiring the complete application or GUI.
2.5 Extensibility
Variable behavior shall be isolated behind appropriate abstractions.
2.6 Performance
The design shall use appropriate data structures for expected simulation workloads without premature optimization.
2.7 Modern C++
The implementation shall make appropriate use of C++23 facilities, RAII, strong typing, standard library containers, and value semantics where appropriate.
2.8 Simplicity
The design shall avoid introducing abstraction or design-pattern complexity that does not provide measurable architectural value.

3. Design Conventions
3.1 Naming
The implementation shall use descriptive names.
Types shall use PascalCase.
Examples:
`PageTable`
`PhysicalMemory`
MemoryManager
`PageReplacementPolicy`
```text

```
Functions and methods shall use descriptive camelCase or the project's established C++ naming convention.
Constants shall use a consistent project-wide naming convention.
3.2 Strong Types
Where practical, semantically different identifiers shall use distinct types rather than interchangeable primitive values.
Examples include:
`ProcessId`
`PageId`
`FrameId`
`VirtualAddress`
`PhysicalAddress`
PageOffset
This reduces accidental mixing of logically different values.
3.3 Const Correctness
Methods and parameters shall use const where appropriate.
Objects that do not require modification shall be represented as immutable or const-qualified values.
3.4 RAII
Resource ownership shall follow RAII principles.
Manual resource management shall be avoided unless required by a specific low-level interface.
3.5 Standard Library
The C++ standard library shall be preferred over custom implementations when it provides an appropriate facility.

14.3 MMU Algorithm
The conceptual algorithm is:
1. Validate the memory-access request.
2. Identify the process.
3. Extract virtual page and offset.
4. Query the page table.
5. If the page is resident:
a. Obtain the physical frame.
b. Update access/reference state.
c. Update dirty state for writes.
d. Construct the physical address.
e. Record the successful access.
6. If the page is not resident:
a. Record a page fault.
b. Obtain a free frame if available.
c. Otherwise request a victim from the replacement policy.
d. Handle the victim page.
e. Load the requested page.
f. Update the page-table mapping.
g. Notify the replacement policy.
h. Complete the memory access.
7. Return a structured result.

17. Page-Replacement Interface
The page-replacement subsystem shall be based on a common abstraction.

```text
────────────────────────────
```

17.1 pageLoaded

20. Clock Design
Clock shall maintain:
An ordered collection of candidate frames.
A clock-hand position.
A reference bit for each candidate.
Conceptually:
```text
┌───────┐
│  F1   │
│ Ref=1 │
└───┬───┘
│
┌─────────┴─────────┐
│                   │
┌────▼────┐         ┌────▼────┐
│   F4    │         │   F2    │
│ Ref=0   │         │ Ref=1   │
└────▲────┘         └────┬────┘
│                   │
└─────────┬─────────┘
│
┌───▼───┐
│  F3   │
│ Ref=0 │
└───────┘
```
When selecting a victim:
Inspect the frame at the clock hand.
If its reference bit is zero, select it.
If its reference bit is one, clear the bit.
Advance the clock hand.
Continue until a victim is found.
The exact state representation shall be finalized during implementation.

21. Optimal Design
Optimal replacement requires knowledge of future accesses.
The implementation shall therefore distinguish Optimal from policies that operate solely on historical state.
The design should provide Optimal with access to the future workload information through an appropriate abstraction.
The replacement policy shall not directly control the simulation engine.
Conceptually:
```text
Future Workload
│
▼
Optimal Policy
│
▼
Future Access Information
│
▼
Select Page Used Furthest
in the Future
```
The Optimal implementation shall select the page whose next use is furthest in the future or which has no future use.
Because Optimal is primarily useful as a theoretical benchmark, its implementation should prioritize correctness and clarity over unnecessary optimization.

30. Exception and Error Strategy
The initial design shall distinguish expected operational failures from programming errors.
30.1 Expected Errors
Expected errors include:
Invalid configuration
Invalid process
Invalid address
Unsupported policy
Invalid workload
These should be represented through explicit error handling.
30.2 Programming Errors
Unexpected violations of internal invariants should be detected through assertions, exceptions, or equivalent mechanisms appropriate to the situation.
30.3 Error Messages
Error messages shall provide useful context.
For example:
Invalid virtual address:
ProcessId=100
Address=0xFFFFFFFF
Reason=Address outside configured virtual address space
The final error model shall be selected during implementation planning.

31. Invariants
The following invariants shall be maintained.
31.1 Page-Frame Mapping
A resident page shall map to exactly one physical frame.
31.2 Frame Occupancy
An occupied frame shall contain at most one resident page.
31.3 Mapping Consistency
If a page-table entry indicates that a page is resident, the corresponding physical frame shall identify that page.
31.4 Free Frame Consistency
A free frame shall not be referenced by a resident page-table entry.
31.5 Replacement Consistency
A replacement policy shall not select a frame that does not correspond to a valid replacement candidate.
31.6 Process Isolation
A process shall not access another process's virtual address space unless such behavior is explicitly introduced as a future requirement.

34. Optimal Algorithm and Workload Interaction
Optimal replacement introduces a special design consideration.
Normal replacement policies require knowledge of current and historical state.
Optimal replacement requires knowledge of future accesses.
The preferred design is to represent the memory-access sequence as an ordered stream with sufficient information to determine future accesses.
Conceptually:
```text
Memory Access Stream
────────────────────────────
Access 0
Access 1
Access 2
Access 3
Access 4
```
...
```text
Access N
```
The Optimal policy may use an immutable or controlled view of the remaining access stream.
The policy shall not be given unrestricted control over the simulation engine.

38. Threading Model
The initial EMMUS implementation shall use a single-threaded simulation model unless a later requirement demonstrates a clear need for concurrency.
The reasons are:
Deterministic behavior
Easier testing
Easier debugging
Simpler state management
Lower architectural complexity
Parallelism may be considered later for independent simulation comparisons or analysis workloads, but it shall not be introduced into the core memory-management model without justification.

39. Persistence
The initial EMMUS system shall not require persistent simulation state.
Simulation configuration may be loaded from files, but the core simulator shall operate in memory.
Future persistence requirements may include:
Saving simulation results
Exporting statistics
Saving workload definitions
Such capabilities shall be added only when justified by requirements.

46. Design Pattern Constraints
Design patterns shall not be used merely to make the project appear more sophisticated.
For every nontrivial pattern, the implementation should be able to answer:
What problem does this pattern solve?
What dependency or variation does it isolate?
Does it improve maintainability or extensibility?
Would the design be simpler without it?
If those questions cannot be answered convincingly, the pattern should not be introduced.

48. Module Dependency Rules
The following dependency rules shall be enforced:
Presentation components may depend on application interfaces.
Application components may depend on simulation interfaces.
Simulation components may depend on memory-management interfaces.
Core memory-management components shall not depend on presentation components.
Replacement policies shall not depend on GUI or CLI components.
Page tables shall not depend on replacement-policy implementations.
Physical memory shall not depend on presentation components.
Infrastructure services shall be accessed through appropriate abstractions where practical.
Test code may depend on production components but production code shall never depend on test code.
Circular dependencies shall be avoided.

49. Implementation Constraints
The implementation shall:
Use C++23.
Follow RAII principles.
Prefer standard-library facilities.
Minimize raw owning pointers.
Maintain const correctness.
Avoid global mutable state.
Avoid unnecessary singleton objects.
Avoid hidden dependencies.
Keep interfaces focused.
Keep classes cohesive.
Maintain automated tests as components are implemented.

51. Detailed Design Review Criteria
Before implementation begins, the detailed design shall be reviewed against the following criteria:
Every major architectural component has a defined responsibility.
Every major interface has a defined purpose.
Component ownership is understood.
Object lifetime is understood.
Major data structures have been selected or constrained.
Memory-access flow is defined.
Page-fault behavior is defined.
Dirty-page behavior is defined.
Replacement-policy behavior is defined.
Optimal-policy requirements are addressed.
Configuration flow is defined.
Statistics flow is defined.
Logging flow is defined.
Error-handling responsibilities are defined.
Testing boundaries are defined.
Dependency direction is understood.
Threading assumptions are defined.
Deterministic simulation behavior is addressed.
The design does not unnecessarily depend on the GUI.
The design avoids unjustified complexity.
The design remains traceable to Phase 1 requirements.
The design remains consistent with Phase 2 architecture.
