# Requirements traceability matrix

This matrix maps the requirement IDs already recorded in EMMUS documentation to current source and test evidence. It is a navigation aid, not a claim that every story is complete or exhaustively proven. “Implemented” describes observed source functionality; “verified” is limited to the evidence listed. The project does not contain a separate formal requirements database, so descriptions are concise summaries of the in-repository story/evidence artifacts.

## Coverage gaps to retain during review

- No interactive GUI or general-purpose CLI is present; `emmus-demo` is a dedicated demonstration executable.
- Normal simulation does not provide Optimal with a future access trace.
- No stable benchmark results, performance thresholds, memory-footprint measurements, or repeated-run analysis are checked in.
- Some component requirements lack dedicated end-to-end assertions.
- Documentation consistency and links are reviewed manually.

When implementation changes, update the matching row and evidence workflow. Do not convert a partial or missing test mapping to “verified” solely because the corresponding type or method exists.
