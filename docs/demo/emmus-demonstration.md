# US-1504: EMMUS portfolio demonstration

This short walkthrough is the project's evaluator-facing entry point. It uses
the shipped C++23 core, checks a controlled trace against known outcomes, then
reports results generated by a seeded full simulation. It is a text-based
demonstration, not a windowed GUI.

## Clean-environment workflow

Prerequisites: CMake 3.24+, Ninja, a C++23-capable compiler, Git, and network
access for the first test-enabled configure (CMake fetches the project’s pinned
GoogleTest revision).

From a clean checkout, at the repository root:

```sh
cmake --preset debug
cmake --build --preset debug --parallel
ctest --preset debug --no-tests=error
./build/debug/bin/emmus-demo
```

The normal presets enable tests and build the `emmus-demo` executable by
default. CTest includes `emmus-demo-smoke`, which runs the walkthrough and
checks the controlled trace. Repeat the same commands with `release` in place
of `debug` to verify the optimized build.

## Five-minute presentation script

### 1. Establish scope and architecture

Run the demo and start with its purpose and architecture summary:

```text
workload -> access executor -> MMU -> page table / physical frames + policy
         -> statistics and typed activity log
```

EMMUS models virtual-page references, mappings, frame allocation, faults,
replacement, and counters. It does not emulate a kernel, TLB, backing store,
or data-bearing memory. This boundary matters when interpreting both behavior
and timings.

### 2. Prove page faults and replacement differences

The demo drives the real MMU with one process, five registered pages, three
frames, and this ordered reference string:

```text
1 2 3 4 1 2 5 1 2 3 4 5
```

The first reference is a write; the others are reads. Expected fault counts:

| Policy | Page faults | What the result demonstrates |
|---|---:|---|
| FIFO | 9 | Evicts the oldest loaded resident page. |
| LRU | 10 | Access recency changes which page is evicted. |
| Clock | Deterministic result printed by the demo | Uses referenced bits and a second-chance hand. |
| Optimal | 7 | Uses the supplied complete future trace; this is the trace's true lower bound. |

The executable checks the FIFO, LRU, and Optimal counts and exits with an
error if they differ. Clock is reported from the actual policy implementation
but is not hard-coded as a separate expected number. The controlled report
also prints replacement/dirty-eviction counters, measured policy decision
time, a per-frame occupancy diagram, utilization percentage, and typed fault,
replacement, and dirty-eviction events.

Illustrative frame display:

```text
[F0:P4] [F1:P5] [F2:P2]
Utilization: 3/3 (100.0%)
```

Frame contents depend on policy; the output is a snapshot from that run, not
the illustration above.

### 3. Observe a complete simulation

The demo next runs the configured locality workload through `Simulation`:

| Setting | Value |
|---|---:|
| Processes | 2 |
| Registered pages/process | 8 |
| Physical frames | 4 |
| Accesses | 64 |
| Workload seed | 1504 |
| Policy | LRU |

Progress updates show accesses, faults, and occupied frames. The final report
shows observed page-fault rate, replacements, dirty evictions, elapsed
simulation time, frame occupancy, and representative events from the
simulation activity log. The access/fault counts are reproducible for this
seed and build; elapsed time varies by machine and build configuration.

### 4. Compare policy effectiveness and cost

The comparison uses one shared 256-access locality benchmark configuration
(one process, eight pages, four frames, seed 1504) and runs FIFO, LRU, Clock,
and Optimal. Read fault totals/rates as workload outcomes and replacement
decision/total simulation times as observations from this invocation.

**Interpretation limit:** the normal `SimulationComparison` path does not
provide Optimal with future references. Its Optimal row is therefore not a
theoretical lower bound. Only the explicitly traced scenario in step 2 supplies
Optimal with the complete future sequence. The time values are one-shot
measurements, not a controlled benchmark, performance claim, or regression
threshold; see [measurement caveats](../verification/testing-and-performance.md).

### 5. Verify engineering evidence

The initial CTest command runs the unit, integration, system, and demo-smoke
tests. The project's requirements-to-code-to-test map is the
[traceability matrix](../requirements/requirements-traceability-matrix.md).
For deeper review, follow links there to the MMU, policy implementations,
statistics, and corresponding test suites. Test presence and a passing run
provide evidence, not a claim of exhaustive proof.

## Expected checks and interpretation

- The controlled run processes all 12 references successfully.
- The verified counts are FIFO 9, LRU 10, and Optimal 7 page faults.
- All policies receive the same ordered references and frame capacity.
- The seeded full simulation processes the configured 64 accesses.
- Each benchmark policy receives the same workload dimensions, access count,
  and seed; measured durations are expected to vary.
- Occupancy and activity are snapshots/events from implemented components;
  no physical-byte contents or backing-store operations are simulated.
